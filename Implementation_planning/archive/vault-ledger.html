01 — Start here

The short version

Two back-to-back phases (5.5, then 5.6) moved every password, API key, client secret, and token that hAIsir's deploy stack uses out of plaintext .env/.env.config.sh files and into OpenBao, a self-hosted secrets vault. That work is fully done and live-verified on dev. It has never been run against staging or prod — those two environments are sitting in a deliberately "cannot start" state until someone runs the bring-up steps in §6.

Three things to hold onto as you read the rest of this:

  • The goal was never "delete the .env files." They still exist, in all three environments, and they still hold real configuration — ports, hostnames, image tags. What left them was only the secret-shaped values.
  • Dev proves the mechanism works. It doesn't mean staging/prod are configured. Each environment runs its own separate OpenBao — dev's doesn't feed staging or prod. Nothing was auto-propagated.
  • The system is deliberately fail-closed. If a secret isn't in OpenBao when something needs it, that something refuses to start rather than quietly running broken or empty. This is why staging/prod can't come up right now — and it's the correct, intended behavior, not a bug you need to route around.

02 — Scope

What moved, what stayed

Every environment file splits into two kinds of line. This project only ever intended to touch one of them.

Stayed in .env / .env.config.shMoved to OpenBao
Ports, hostnames, domain namesDatabase passwords (POSTGRES_PASSWORD, KEYCLOAK_POSTGRES_PASSWORD, KC_DB_PASSWORD)
Docker image tags, registry URLKeycloak admin password & OIDC client secret
CIDR allow-lists, network subnetsAPISIX admin key, session secret, CrowdSec bouncer key
Non-secret usernames (KC_DB_USERNAME, POSTGRES_USER)Backend-admin Keycloak client credential
Feature flags, model spec strings, timeoutsTest-user password, Cloudflare tunnel token
pgadmin dev credentials out of scopeGoogle OAuth client ID/secret, LLM API keys, CSRF secret

pgadmin is the one deliberate exception. It's a dev-only convenience tool that doesn't exist in staging or prod at all — migrating it would have added OpenBao plumbing for a credential with no real blast radius. Left as plaintext, on purpose, dev-only.

Why this split matters for you

If you ever wonder "should X move to OpenBao?" — the test isn't "is it in an .env file," it's "does this value grant access to something, and would I care if it leaked or want to rotate it?" Ports and image tags fail that test. Passwords and tokens pass it. See §8 for the full decision framework.

03 — Mechanism

How a secret actually reaches a container

OpenBao doesn't hand out secrets to just anyone who asks. Two kinds of caller authenticate to it, and secrets get to a running container by one of two paths, depending on when they're needed.

Who's allowed to ask

  • Machines authenticate with an mTLS client certificate — a per-service identity (backend, worker, deploy, db, keycloak-db, keycloak) issued from hAIsir's own CA. No matching certificate, no connection at all — OpenBao's TLS listener refuses the handshake before a password or token is ever considered.
  • Humans are meant to log in via Keycloak OIDC. In practice that path is currently broken (the listener's mTLS requirement blocks a plain browser before OIDC is reached — see §7), so a stand-in mTLS identity called admin-ops is used instead, on dev.

Path A — deploy-time templating (the majority of secrets)

Before docker compose up ever runs, a script called render-deploy-secrets.sh logs in as the deploy identity, reads everything it's allowed to see across six KV paths, and prints it as KEY=value lines. Two other scripts consume that output:

  • env-setup.sh merges it with the non-secret .env values into a short-lived file used as compose's --env-file — never written to disk longer than the one command needs it.
  • template-configs.sh uses it to fill in {{PLACEHOLDER}} tokens inside the APISIX and Keycloak JSON config templates (things like the admin API key).

This path fails closed twice: once if OpenBao is unreachable or completely unseeded, and again — key by key — against a manifest file (deploy-required-keys.txt) that names every secret each environment must have before deploy is allowed to proceed. A half-migrated state (removed from .env but not yet in OpenBao) is not representable; the render aborts first.

Path B — Vault Agent sidecars (secrets a container needs at the moment it boots)

Five services can't wait for a deploy-time render because they need their secret the instant the container starts, every time it restarts: backend, worker, db, keycloak-db, and keycloak. Each gets a small companion container — a Vault Agent sidecar — that logs into OpenBao with that service's own certificate and continuously renders its secret to a file the real container reads:

  • backend / worker → a full env file, read via SETTINGS_ENV_FILE.
  • db / keycloak-db → a one-line file wired in as Postgres's own POSTGRES_PASSWORD_FILE mechanism.
  • keycloak → a fully rendered keycloak.conf — this one has zero password environment variables at all.

The container is never started until its sidecar reports healthy (a service_healthy dependency plus a test -s /secrets/… healthcheck) — so an unreachable or unseeded OpenBao blocks the boot instead of letting the container start with a missing or blank password.

A naming note, if you read the task history

Internally this project calls Path-A-style secrets "Class A" and the five Path-B cold-start services "Class B." They were deliberately sequenced — all of Class A had to pass a full live rehearsal before Class B was touched, because Class B is the riskier change (get it wrong and the database itself won't boot).

05 — Verification

Proving it works, on dev

None of this was taken on faith. Dev passed two structured "hard gates" — a live rehearsal that everything downstream was blocked on — before being called done.

  • passed Class A gate: cold bring-up from scratch, config-file hashes verified against KV, an APISIX admin-API auth probe, a full browser-style OIDC login exercised end-to-end, the backend-admin credential checked for drift, and a scan for leftover plaintext.
  • passed Class B gate: a cold bring-up with existing data preserved, and a completely fresh-volume first-boot in an isolated sandbox, a docker inspect check that no password ever appears as a container environment variable, a sealed-OpenBao fail-loud drill, and a break-glass (emergency plaintext restore) drill.

You can re-run the same proof yourself at any time — these live as real scripts, not just notes:

# zero secret-shaped values remain in any .env file, in any environment
bash common/scripts/tests/full-plaintext-elimination-scan.sh

# no password ever shows up in `docker inspect`, by variable name only
bash common/scripts/tests/docker-inspect-exposure-check.sh

# rendered config files match what's actually in OpenBao (hash compare, no values printed)
bash common/scripts/tests/templated-config-hash-verify.sh
Also fixed along the way

Live rehearsals are useful precisely because they surface real bugs pre-existing config gaps couldn't hide from anymore. This project found and fixed three of them as root cause: a 7-month-stale image tag, an unwired HTTPS-enforcement setting, and a missing container permission that made Keycloak crash-loop on its very first real boot. None were secrets bugs — they were exactly the kind of thing a "just believe it works" migration would have shipped silently.

06 — Runbook

Deploying to staging & prod

Both environments already have OPENBAO_DEPLOY_SECRETS=true set in their .env.config.sh — that flag was flipped on across all three environments together, back in Phase 5.6. What's missing isn't configuration, it's infrastructure that has simply never been started. Neither staging's nor prod's OpenBao container has ever run. Until it does, any deploy attempt will correctly abort at the render step.

Before you start

Run every step below against each environment separately — staging and prod each run their own OpenBao instance with no relationship to dev's or each other's. Never copy a secret value from dev's KV into staging or prod; every value must come from that environment's own live, currently-in-use credential.

  1. Confirm prerequisites

    Docker, the external haisir-net network, and hAIsir's root CA all need to exist on that host already (generate-certs-ca.sh if the CA is missing).

  2. Issue certificates

    Generate the server certificate plus one client certificate per machine identity. Make sure the identity list includes the Class B ones — dev only discovered it needed db, keycloak-db, and keycloak identities partway through Phase 5.6, so don't rely on the script's older default list:

    OPENBAO_CLIENT_IDENTITIES="backend worker deploy db keycloak-db keycloak admin-ops" \
  bash common/scripts/certs/generate-certs-openbao.sh <env-dir>

  3. Start the OpenBao service

    APP_ENV=<staging|prod> DOMAIN_NAME=<domain> \
  docker compose -f common/openbao/docker-compose.openbao.yml up -d

  4. Bootstrap and immediately secure the recovery material

    APP_ENV=<env> bash common/openbao/bootstrap.sh all

    This writes .bootstrap-out/<env>/server-init.json — the recovery keys and root token. Move it offline (password manager, sealed envelope) immediately and delete the local copy. It's gitignored, but that's not the same as safe.

  5. Verify it's actually unsealed

    APP_ENV=<env> bash common/openbao/bootstrap.sh status

  6. Write policies and register the machine identities

    APP_ENV=<env> bash common/openbao/bootstrap.sh configure

  7. Seed every KV path — with that environment's real, currently-live values

    APP_ENV=<env> bash common/openbao/bootstrap.sh seed-deploy-path gateway \
    APISIX_ADMIN_KEY SESSION_SECRET CROWDSEC_BOUNCER_KEY

APP_ENV=<env> bash common/openbao/bootstrap.sh seed-deploy-path keycloak \
    KEYCLOAK_CLIENT_SECRET GOOGLE_OAUTH_CLIENT_ID GOOGLE_OAUTH_CLIENT_SECRET \
    KEYCLOAK_ADMIN_PASSWORD KC_DB_PASSWORD KEYCLOAK_POSTGRES_PASSWORD
    # staging only, add: TEST_USER_PASSWORD

APP_ENV=<env> bash common/openbao/bootstrap.sh seed-deploy-path keycloak-clients \
    KEYCLOAK_BACKEND_ADMIN_CLIENT_ID KEYCLOAK_BACKEND_ADMIN_CLIENT_SECRET

APP_ENV=<env> bash common/openbao/bootstrap.sh seed-deploy-path db \
    POSTGRES_PASSWORD

APP_ENV=<env> bash common/openbao/bootstrap.sh seed-deploy-path infra \
    TUNNEL_TOKEN

    Values are piped in over stdin and never appear in shell history or process listings. Verify a seed landed correctly by hash-comparing, never by printing the value:

    bao kv get -format=json secret/haisir/<path> | jq -r '.data.data.KEY' | sha256sum
# compare against: printf '%s' "$THE_REAL_VALUE" | sha256sum

  8. Deploy as normal

    With every path seeded, the existing deploy scripts (setup.sh, setup-keycloak.sh, deploy.sh) now succeed — render-deploy-secrets.sh can resolve everything they need. No deploy-script changes are required for this step; it "just works" once OpenBao itself is populated.

    Known snag

    A standalone setup.sh invocation currently fails under set -u before it gets the chance to render from OpenBao (see §7, item 1). If you hit an "unbound variable" error on APISIX_ADMIN_KEY, source the render hook manually first — see §7 for the exact workaround dev used.

  9. Re-run the same verification dev used

    The scripts in §5 aren't dev-specific — run full-plaintext-elimination-scan.sh and docker-inspect-exposure-check.sh against staging/prod too, once they're up.

  10. Rotate what you just typed in

    Whatever you seeded in step 6 was, by necessity, typed by a human during bring-up. Treat it as a first, temporary value — rotate every one of those secrets for real once the environment is confirmed live, the same discipline dev's own closeout used (rotate-secret.sh, documented per-secret in the rotation runbook — see §10).

07 — Honesty section

What's still open

Five things were found while this migration was underway. Two — the stale README and the dead config leftover — have since been fixed. The rest are deliberately not fixed — either because they were out of scope for a secrets-only phase, or because fixing them wasn't worth the risk this late in closeout. Know about all of them before they surprise you.

1. setup.sh checks a secret before it renders one

open The script checks that APISIX_ADMIN_KEY is non-empty before it runs its own OpenBao render step. Now that the plaintext fallback is gone, a bare bash setup.sh invocation fails with an "unbound variable" error under set -u. Workaround used on dev: source the render hook manually first —

source common/openbao/render-secrets-hook.sh
render_deploy_secrets_or_die
bash setup.sh # now succeeds

2. Two Docker networks that don't talk to each other, on dev

open common/docker-compose.yml hardcodes the network name haisir-net, but the documented dev setup creates haisir-net-dev — so the dev stack and the shared common project sit on two disconnected networks by default. Worked around live with docker network connect, never fixed in the compose file. This is a dev-sandbox-specific issue (single-host, two compose files) — it's unlikely to bite staging/prod, which typically run one compose file per host, but worth knowing if that ever changes.

3. The OpenBao README's own opening section was stale

fixed common/openbao/README.md's top ("Layout", "Bring-up", "Auto-unseal") described the original two-instance transit-auto-unseal design, replaced by a simpler built-in static seal back in Phase 5.5 — the file had only ever been extended with newer sections further down, never rewritten at the top to match. Rewritten: Layout/Bring-up/Auto-unseal now describe the single-instance static-seal design; the machine-identities table gained the four identities it was missing (db, keycloak-db, keycloak, admin-ops); the KV secret-layout table was corrected to match deploy-required-keys.txt and the actual policy files (it had KEYCLOAK_POSTGRES_PASSWORD under the wrong path and was missing the keycloak-clients path entirely); the Phase-4 backup section referenced a backup.sh --with-unseal flag that doesn't exist in the script and a restore command using docker cp (broken on rootless Docker, same trap this repo already worked around everywhere else). All fixed directly in the README — no more "trust the bottom over the top" caveat needed.

4. A dead, harmless leftover in dev's config

fixed dev/.env.config.sh had a TUNNEL_TOKEN line with a placeholder test value. It was inert — nothing in the compose stack read TUNNEL_TOKEN from that file; the real Cloudflare tunnel service renders its own copy from OpenBao independently. Deleted.

5. Human login to OpenBao itself doesn't work as documented

open The OIDC login path described in the README doesn't actually work — the server's mTLS requirement rejects a plain browser connection before Keycloak OIDC is ever reached. The admin-ops mTLS identity (§4) is the working substitute today, on dev only. Repeat that identity's setup for staging/prod during their bring-up (§6, step 2's identity list already includes it).

08 — How-to

Adding your own secret

Yes — you can move more values into OpenBao yourself. Nothing about the mechanism is specific to the ~15 secrets already migrated; it's a general pattern. Two questions decide how much work it is.

First: is it actually a secret?

Ask "does this value grant access to something, or would I want to rotate/audit it?" Passwords, API keys, tokens, client secrets — yes. Ports, hostnames, image tags, feature flags, timeouts — no. Moving a non-secret value into OpenBao buys you nothing and adds a hard dependency: now that value can't be read at all if OpenBao is down, for zero security benefit. Leave those in .env/.env.config.sh.

If it's a deploy-time secret (Path A, §3)

This covers anything templated into an APISIX/Keycloak config file or read directly by compose before startup — the same shape as most of the ledger in §4.

  1. Pick an existing KV path if an identity that already needs this value exists (gateway, keycloak, infra, …), or add a new path — meaning adding it to the loop in render-deploy-secrets.sh — if it deserves its own least-privilege boundary.
  2. Seed it: bootstrap.sh seed-deploy-path <path> <KEY>.
  3. Reference <KEY> by the same name wherever it needs to land — a {{KEY}} placeholder in a JSON template, or a bare ${KEY} in compose, exactly like the existing keys.
  4. If it must never silently be empty, add <path>:<KEY> as a line in deploy-required-keys.txt so the fail-closed gate covers it too.
  5. Only after confirming the OpenBao-sourced value actually resolves correctly (hash-compare it, never diff the raw value) — delete the plaintext from .env.config.sh/.env. Never remove-then-seed; always seed-then-remove.

If it's read directly by the backend or worker (Path B, §3)

  1. Seed it into secret/haisir/backend, /worker, or /shared, whichever identity actually needs it.
  2. Add a line to that identity's Vault Agent template (common/openbao/agent/templates/*.ctmpl) so the sidecar renders it into the env file the app reads.
  3. Confirm that identity's policy file already covers the KV path — it will, if you reused an existing one.
  4. Restart the sidecar and the app container. A re-render never restarts the consumer on its own — there's no automatic reload wired up.
  5. Then, and only then, delete the plaintext.

If it's a brand-new cold-start password for a service that doesn't have one yet

This is the heaviest case — it's what db, keycloak-db, and keycloak needed this phase: a new machine identity, a new policy, a new Vault Agent sidecar, and — critically — proof that the target software actually supports reading its password from a file at all before you build around that assumption. Don't skip the proof step. Use the Class B spike write-ups (common/openbao/class-b-mechanism-spikes.md and class-b-delivery-mechanism-decision.md) as the template to repeat, not as history to skim past.

09 — For reference

Glossary

OpenBao
An open-source secrets vault (a fork of HashiCorp Vault) — a server that stores secrets encrypted and only ever hands one out to a caller it can verify and that's explicitly permitted to read it.
KV v2
OpenBao's key-value secret engine, version 2. A simple path → {key: value} store, with version history kept automatically.
mTLS client certificate
Mutual TLS — both sides of a connection present a certificate, not just the server. A machine's certificate acts as an unforgeable ID card: no valid cert, no connection, checked before any password or token is even considered.
Static seal
How OpenBao decrypts its own storage after a restart, using a key file stored locally rather than requiring a human to type in unlock shares by hand every time it reboots.
Vault Agent sidecar
A small companion container that logs into OpenBao on the main service's behalf and continuously writes the secrets it's permitted to read to a file — the main application container never talks to OpenBao directly.
Fail-closed
If a required secret is missing or empty, the system refuses to start rather than starting anyway with a blank or dummy value standing in for it.
Hard gate
A checkpoint in the rollout that everything downstream is blocked on, until it's proven working live — not just believed to work from code review alone.
Class A / Class B
Project-specific shorthand, not an OpenBao term. Class A = secrets templated in before docker compose up even runs (§3, Path A). Class B = the three cold-start database passwords a container needs the instant it boots, delivered as files by dedicated sidecars (§3, Path B).
