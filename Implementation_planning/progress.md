## Target State

This increment targets three personas only: **Student**, **Parent**, and **Platform Admin**. Institutions, instructors, tutors, classes, doubts, hAITU, and notifications are explicitly deferred.

**Essay AI Grading (newly added — Phase 1 backend + deploy only; Phase 2 UI deferred):** `essay` questions are now evaluated by an async AI-grading pipeline that reuses the existing LLM provider infrastructure (`glm-ocr` / Ollama pattern). The exam owner sets `essay_grading_mode` per exam template (`auto_release` default: AI score released to student immediately; `review_first` opt-in: score held until owner confirms). A per-question analytic rubric (JSONB, 3–6 weighted criteria with per-level descriptors) may be attached; if absent, a built-in default is selected by `essay_subtype`. The LLM outputs per-criterion levels only; the backend computes `ai_score = Σ(level/scale_max × weight) × points` (no LLM arithmetic). The worker polls `essay_grading_jobs` (new table, same `FOR UPDATE SKIP LOCKED` pattern as extraction) and writes `ai_score`, `ai_feedback`, `ai_rationale` to `exam_session_questions`. Students can dispute released AI grades; exam owners (parent for parent-owned exams, admin for platform exams) can confirm or override. A `GradingSettings` config block mirrors `ExtractionSettings` with `GRADING__MODEL_SPEC` defaulting to `qwen3:14b` (local, PII on-prem); Ollama-cloud (`gpt-oss:120b-cloud`) and `anthropic://` are opt-in. Schema: V29 migration adds 3 columns to `questions`, 1 to `exam_templates`, 9 to `exam_session_questions`, plus the `essay_grading_jobs` table. Auth: 2 new security rules (BR-SEC-011, BR-SEC-012) plus permission matrix rows for dispute (student/parent) and override/confirm (owner only). Instructor/tutor grading deferred until role migration.

Content is tagged with an `owner_type` discriminator (`'platform'` or `'parent'`) and `owner_id` (NULL for platform; parent `idp_sub` for parent-owned), added via additive `ALTER TABLE` to `course_path_nodes`, `topics`, and `exam_templates`. Platform Admin manages the authoritative platform board (arbitrary-depth `course_path_nodes` tree, topics, exam templates with `owner_type = 'platform'`). Topic content is created in two ways: (a) instant types — video URL and pasted text — written directly to `topic_contents`; (b) **extraction types — PDF and image — uploaded via multipart, queued in `extraction_jobs`, picked up by a worker process that uses `pypdfium2` for native PDF text and `glm-ocr` (vision LLM) for scanned PDFs / images, then materialized as N `topic_contents` rows of `content_type='text'` with permanent provenance back to the source filename via `source_extraction_job_id` + indefinite `extraction_job_audit`.** Students see two sections on their dashboard: "Platform Board" (blue) containing all platform content, and "Home Study" (green) containing content from their linked parent — visible only if an active `parent_child_links` record exists. Parents are content creators: they can adopt a platform board subtree (deep clone of nodes + topics only; content and exams not cloned) or build their own curriculum from scratch, upload notes per topic (extraction pipeline is shared with admin, gated by per-parent quota), and create private exams. Parent content is visible only to their linked child. Parents view child exam results for their own exams only (not platform exams). Token refresh after role assignment uses explicit logout (`/auth/logout`) — not `prompt=none`. Auth is APISIX-injected JWT with `X-Current-Role` header and CSRF on all mutations; identity is `idp_sub` (Keycloak `sub` as raw UUID string) with no local users table. The backend independently verifies each JWT: local JWKS RS256 decode is the fast first gate, and — when `introspection_enabled` — a feature-flagged OAuth2 token introspection call (RFC 7662) confirms the token is still active, catching revocation that stateless validation cannot. Introspection uses the existing `haisir-backend-admin` service-account client, caches results per token for a short TTL, and fails closed (Keycloak unreachable → 503, inactive → 401); Keycloak 26 requires the `token-introspection` scope and the backend client in the token `aud`, provisioned declaratively by deploy (see decisions.md 2026-06-02, TASKS.md G14). The `questions.question_type` enum is extended with three new values: `one_word_response` (compact inline input, auto-graded by normalized match), `matching` (two-column pair UI, partial credit per pair, right-column shuffled per-session using seeded Fisher-Yates with seed stored in `exam_session_questions.shuffle_seed`), and `problem_solving` (auto-graded final answer + optional working area captured in `exam_session_questions.working_text` but unscored this phase — instructor scoring deferred). The `essay` type gains an `essay_subtype` column as a rendering hint; valid values: `analytical`, `critical`, `extended`, `narrative`, `reflective`, `short` (6-value enum enforced by DB CHECK constraint). Schema additions via V27+V28: `questions` gains `essay_subtype VARCHAR(50) NULL` (widened from initial `VARCHAR(10)` in V28 with CHECK constraint), `working_required BOOLEAN DEFAULT false`, and `penalty_matching BOOLEAN DEFAULT false` (enables score-reduction mode for matching: `max(0, (correct − wrong) / total) × points`); `exam_session_questions` gains `working_text TEXT NULL` and `shuffle_seed INT NULL`. (See `target/2026-06-05_question_types_extension.md`.)

**Gateway WAF modernisation, CSP & security-review closeout (newly specced — Phase 7, spec-only, not yet implemented):** the Coraza WAF at the APISIX gateway is upgraded, its exclusions rewritten from blanket rule-removal to field-scoped targeting, and the application payloads that made those exclusions necessary are removed at the source. Scoping (2026-07-27) established a mechanical root cause for the near-daily false-positive tuning: regex collection keys in `ctl:ruleRemoveTargetById` landed in **Coraza v3.5.0**, but the shipped build pins **v3.3.3** via `coraza-proxy-wasm 0.6.0` — so every attempt at a field-scoped exclusion was parsed as a literal variable name and silently matched nothing, which is why the workaround escalated to whole-request `ctl:ruleRemoveById` and grew to **38 rule IDs** across seven rounds in nine days on `POST /api/haitu/(topic-doubt|exam-review-chat)`, and, separately, an anomaly-threshold raise (5→12) plus 50 MB argument-size limits on `12-api-exams-static.json` to admit base64 images (that route's *field* exclusions use the correct `SecRuleUpdateTargetByTag <tag> "!ARGS_POST:/field/"` form and are preserved). The same scoping pass found that **CRS 4.14.0 carries CVE-2026-21876** (CVSS 9.3, multipart charset bypass in rule 922110, fixed 4.22.0 on 2026-01-06) and that `tx.total_arg_length=65535` with rule 920390 unexcluded is a hard ceiling further tuning cannot clear. `coraza-proxy-wasm` is vendored into `haisir-deploy/gateway-docker/` as a maintained fork (replacing a build-time `git clone` plus an awk script that rewrites upstream `plugin.go` by pattern match), Coraza moves to ≥v3.5.0 and CRS to ≥4.25.1 LTS, and a hard gate proves both the CVE fix and field-scoped exclusion behaviour before any exclusion is retired. Alternatives were evaluated and rejected with reasons recorded so they are not re-litigated: **SafeLine** (semantic engine genuinely solves the prose false-positive class, but closed-source non-EU binary, out-of-process, ~5 stateful containers; prior POC abandoned) and **open-appsec** (the earlier "monitors only for 7–14 days" finding is *wrong* — the model ships pre-trained and Prevent mode works from day one — but it is Israeli/Check Point rather than European as assumed, out-of-process, still needs a custom APISIX image, and its production-recommended model is a portal download). CrowdSec virtual patching is adopted as a Phase 8 complement, not a replacement; the deployed CrowdSec integration is IP-reputation only today. In parallel, **Content-Security-Policy** — absent everywhere despite six other security headers being enforced at the gateway — is added as a nonce-based policy in the frontend's existing `src/proxy.ts`, not at the gateway: a per-request nonce cannot be minted by APISIX and injected into rendered HTML, so a gateway CSP would necessarily be static and force `script-src 'unsafe-inline'`. This is cheaper here than usual because styling is 112 CSS Modules with no CSS-in-JS and there are no inline scripts or third-party script origins, though only 15 of 27 pages currently carry `force-dynamic` — the other 12 (including all of `/onboarding/*` and `/admin/*`) are statically prerendered and must be opted into dynamic rendering before enforcement, since a build-time-rendered page cannot receive a per-request nonce (BR-CSP-010); the existing `csp-report` route is dead scaffolding that discards reports and must persist them before the Report-Only soak. Application-side design fixes end the false-positive source: `exam-review-chat` gains server-side persistence (it is fully stateless today, so this is new storage, not a refactor), `topic-doubt` stops replaying history the server already writes to `doubt_messages`, exam images move from base64 `data:` URIs to URL references, free-text fields gain `max_length`, and `ReviewChatMessage.role` is constrained to a `Literal` — closing a live prompt-injection hole that let a client inject a `system` turn into an authenticated LLM call, which no WAF can see. Finally, every surviving finding from `security/SECURITY_REVIEW_2026-07-02.md` is fixed or documented as accepted, including a new one that review missed: `OAUTH__KEYCLOAK__SSL_VERIFY=false` in prod and staging disables TLS verification on the backend's token-introspection channel, contradicting BR-SEC-010's fail-closed guarantee. Two new business-rule prefixes (`BR-WAF-*`, `BR-CSP-*`) plus BR-SEC-020/021; the pre-existing BR-SEC-011/012 collision between `02_auth_and_roles.md` and `13_secrets_management.md` is recorded rather than renumbered. Only the *gateway builder stage* of the Minimus migration is folded in; the rest stays Phase 8. Specs: `target/requirements/16_gateway_waf.md`, `target/requirements/15_security_headers.md`. Implementation deferred to a future `/implement` cycle.

**Content Viewing & Publish (newly specced — spec-only, not yet implemented):** uploaded content becomes viewable in its native format, and student visibility becomes an explicit per-item publish decision instead of being implicit in the extraction pipeline. A PDF/Image upload now materializes **both** a permanent raw `topic_contents` row (new `content_type` value `'image'` — a native Postgres enum needing `ALTER TYPE contenttype ADD VALUE` in an autocommit block; `'pdf'` already existed in the baseline enum, previously unused for raw storage) whose file path reuses the existing `url` column, **and** the existing N extracted `text` rows — extraction's primary purpose was always RAG embeddings, not display, so the raw form is what's normally published (e.g. a well-formatted textbook page), with the editable extracted text available as a fallback the uploader publishes instead when the raw source is low quality (a poor scan). Exactly one side is published at a time, enforced at the service layer (BR-DATA-024). A new `topic_contents.visibility_status` column (`'draft'`/`'published'`, additive) gates student visibility underneath the existing topic-level `status='live'` gate (BR-DATA-025) — orthogonal to `rag_indexing_outbox` indexing status, which continues to run against every extracted `text` row regardless of its own publish state, since search-groundedness and student display are decoupled. Platform admin and parent both gain the ability to view every upload in both raw and extracted form before choosing what to publish (previously neither could view raw content at all — the source file was purged after extraction). The viewer work is mostly reuse, not new build: `ContentViewer` and `SecurePdfViewer` already exist on the student side and are promoted to shared; only the **image** viewer is net-new. What is genuinely missing is a per-content file-serving endpoint — the existing `GET /api/topic-contents/{content_type}/{topic_id}` is topic-keyed (cannot address one of N+1 rows), hardcodes `application/pdf`, and excludes the parent role, so it is replaced by `GET /api/topic-contents/{content_id}/file` and removed. Two fixes bundled in: a markdown editor with live preview replaces the plain-textarea text editor, and video playback moves from a raw `<iframe src>` (which fails outright for embed-restricted YouTube videos) to the official YouTube IFrame Player API / Vimeo Player SDK with a "Watch on YouTube/Vimeo" fallback link — scope stays YouTube + Vimeo only, matching the existing hostname allowlist. Reverses two prior rules: BR-DATA-008/009 (`01_data_model.md`) and BR-EXT-012 (`12_content_extraction.md`), which asserted the source PDF/image was transient and never stored, and that content was visible to students immediately on creation. By explicit product decision, this ships as a clean reset rather than a backward-compatible migration: `topic_contents` and its dependent extraction/RAG tables are truncated, existing content is discarded, and everything is re-uploaded fresh under the new model — the column default (`visibility_status DEFAULT 'draft'`) reflects that decision; a deployment intending to preserve existing content would instead need `DEFAULT 'published'`, mirroring `topics.status`'s `DEFAULT 'live'`. Specs: `target/requirements/01_data_model.md`, `target/requirements/12_content_extraction.md`, `target/requirements/03_student.md`, `target/requirements/05_parent.md`, `target/requirements/07_platform_admin.md`, both `ui-mapping` files. Implementation deferred to a future `/plan` + `/implement` cycle.
